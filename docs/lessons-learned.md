# 光热发电定日镜场优化 — 经验教训

> 适用场景：数学建模竞赛、工程仿真优化类项目。
> 技术栈：Python + NumPy/SciPy + Numba + matplotlib

---

## 一、建模方法论：先跑通，再优化

### 1.1 三段式递进是最稳妥的节奏

```
问题一（正向模拟） → 问题二（均匀优化） → 问题三（异构优化）
   ↓                    ↓                    ↓
 验证模型正确性      找到全局最优          基于最优解微调
```

**核心原则：每一步的输出是下一步的输入。** 问题二的 warm-start 直接喂给问题三——而不是从零开始。

**教训**：不要一上来就建复杂模型。先用最简单的方式跑通整条链路（哪怕只有 12 个采样时刻而不是 60 个），确认数据能走通、结果大概合理，再逐步加复杂度。

### 1.2 "快速模式"是迭代期的生命线

本项目建了两个时间采样表：
- **完整模式**：12 月 × 5 时刻 = 60 个采样点（用于最终验证）
- **快速模式**：12 月 × 1 正午 = 12 个采样点（用于优化迭代）

```python
schedule = build_noon_schedule()  # 12 个时刻，速度快 5 倍
```

在优化算法每代都要调用目标函数时，用快速模式意味着 5 分钟 vs 25 分钟的区别。

**适用场景**：任何需要多次迭代的仿真优化。快速评估 → 粗筛参数 → 最终验证。

## 二、优化算法实战经验

### 2.1 DE（差分进化）的参数选择

| 参数 | 推荐 | 原因 |
|------|------|------|
| popsize | 5-15 | scipy 要求 > 4，太小搜索不充分，太大太慢 |
| maxiter | 视收敛情况 | 本项目 15 代就收敛了，设 50 太浪费 |
| init | 必须提供 | 用已知好解+扰动构建初始种群，比随机好十倍 |
| polish | True | 最后用 L-BFGS-B 精修，物超所值 |

**坑**：scipy 的 `differential_evolution` 要求 `init` 种群大小 > 4，否则报错。本项目用 popsize=4 时报错 `S > 4`，最小用 5。

### 2.2 "好初值"比"大种群"重要得多

问题三用问题二的最优解做 warm-start，所有环初始 W=6.0, h=3.0，加 10% 扰动打破对称性。结果即使只用小种群（popsize=5）也能快速收敛。

**方法论**：
1. 先用粗粒度搜索（网格/随机）找到大致范围
2. 再用 DE 在好初值附近精搜索
3. 不要指望 DE 从完全随机的初始种群中找到全局最优

### 2.3 异构优化不一定优于均一优化

这是本项目最大的反直觉发现：**给每环独立参数（52 个变量）没有比统一参数（5 个变量）更好。** DE 收敛回均一解。

**教训**：复杂度 ≠ 效果。在建模竞赛中，如果你的复杂模型和简单基线差不多，要么你的简单基线已经很好，要么复杂模型需要换个思路。**不要为了"显得高级"而堆复杂性。**

## 三、数据处理与分析

### 3.1 加权方法严重影响结论

四种加权方式算出年均功率差 9.7%（55.2 ~ 60.6 MW）：

| 方法 | 结果 | 评价 |
|------|------|------|
| sin(α_s) 加权 | 60.58 MW | ✅ 物理合理 |
| 等权重 | 55.23 MW | ❌ 低估，早晚低效时刻拉低均值 |
| DNI 加权 | 56.56 MW | 中等 |

**教训**：加权方式不是"细节"而是"核心假设"。**选加权方法必须有物理依据，不能随意。** 太阳辐射问题用 sin(α_s) 加权是标准做法——太阳低角时辐射本来就弱，那些时刻不该和正午同等对待。

### 3.2 全维度敏感性分析

本项目对 5 个变量做单变量扫描：

```
W（镜宽）： 最敏感 — 偏离 6.0 后 P/A 暴跌
y_t（塔南北）：较敏感 — 南偏优于北偏
h（高度）： 中等 — 越低越好
n_rings（环数）：中等 — 越多功率越高但 P/A 几乎不变
x_t（塔东西）：不敏感 — 对称布局
```

**方法论**：敏感性分析的目的是**识别哪些参数值得花时间精细调，哪些设个差不多就行。** 本项目发现 W 是关键，y_t 次之，但最优解恰好都在物理约束边界附近，说明模型本身对这个问题有明确的偏好。

### 3.3 月度分解发现隐藏问题

年均 60.58 MW 看起来刚好达标，但拆开看：

```
峰值月（6月）：75.0 MW
谷值月（1月）：35.5 MW  ← 只有峰值的一半！
低于 60MW 月份：7/12
```

如果不做月度分解，你会以为"60MW 够了"。但实际上冬季有近 5 个月严重不足，**需要储热系统补约 5000+ MWh**。

**教训**：任何"年均值"都要拆开看时间分布。均值掩盖波动。

## 四、代码工程质量

### 4.1 单位管理

**这是本项目的血泪教训。**

fitness 值在优化器内部是 MW/m² 单位（~ -0.0005），但绘图函数的 baseline 参数是 W/m² 单位（525.85）。结果收敛曲线图上基线差了 100 万倍，完全看不到。

**修法**：在 `plot_convergence_curve` 里乘以 1e6：
```python
fitness = [h['best_fitness'] * 1e6 for h in history]  # MW/m² → W/m²
```

**如何避免**：
- 每个函数 docstring 写清楚输入输出的单位
- 数据文件（CSV）的列名带上单位，如 `P_avg_MW` 而非 `P_avg`
- 全局统一一套单位体系，在 `constants.py` 里定义转换常量

### 4.2 Numba 与多进程的兼容

Numba JIT 编译的函数在 `ProcessPoolExecutor` 子进程中需要每个进程独立编译一次。首次编译有开销（几秒到几十秒），但后续调用极快。

本项目蒙特卡洛用了 5 个并行进程，总耗时 5 分钟（串行大约需要 15-20 分钟），提速 3-4 倍。

**注意**：不要在子进程中共享 Numba 编译的全局对象——让每个进程自己 import 和编译。

### 4.3 模块化结构

```
csp_heliostat/
├── config/       # 常量、采样表
├── core/         # 太阳几何、DNI、大气
├── field/        # 镜面、布局、约束
├── efficiency/   # 各项效率计算
├── simulation/   # 快照仿真、年度仿真
├── optimization/ # 均匀优化、异构优化
├── analysis/     # 敏感性、月度、蒙特卡洛……
└── visualization/# 所有绘图
```

每个模块职责单一。加新分析功能只需在 `analysis/` 下加一个文件，不影响其他模块。

## 五、仿真模型的特殊经验

### 5.1 蒙特卡洛不总是"有波动"

本项目的蒙特卡洛结果：CV = 0.000%。10 次重复仿真结果完全一致到小数点后 6 位。

这说明阴影遮挡算法的随机栅格采样对 **3200 面镜的年均值** 影响可以忽略——大数定律抹平了随机性。

**教训**：跑了蒙特卡洛发现没有波动 ≠ 白跑了。**零方差本身是一个有意义的结论**——它告诉你"这个随机源不需要担心"。

### 5.2 坐标系必须文档化

太阳位置计算涉及多个坐标系：
- 全局坐标系（East-North-Up）
- 太阳方向向量（从镜面指向太阳）
- 接收器方向向量（从镜面指向接收器）
- 法向量（居中于太阳向量和接收器向量）

**本项目在计划文档中明确定义了每个坐标系的原点、轴方向和符号约定。** 这在团队协作时至关重要——每人基于同一套坐标约定写代码。

## 七、DE 优化实战踩坑（Q1-Q6 改进轮次）

> 本轮经历：两阶段 DE 跑了 171 分钟，途中脚本卡死 4 次、f-string 格式错误导致崩溃、multiprocessing+Numba 首代编译缓慢、polish 步骤意外吃掉大量时间。以下是从"脚本写好了但就是不动"到"终于跑完看到 +1% 提升"的血泪教训。

### 7.1 永远先做 Benchmark，不要相信纸面估算

最初的计划估算 noon 评估 = 11 秒，full-60 = 53 秒。**实际 noon = 33 秒**（三倍误差）。

纸面估算的三个盲区：
- 镜场构建开销（3200 个 Mirror 对象创建并非零成本）
- annual_simulation 的 tqdm/打印/数据整理开销
- 每次评估重新构建镜场（而非缓存布局）

**规则**：在任何优化脚本运行前，先跑 **1 次单例评估计时**。用这个实测值重算总耗时。纸面估算 ×3 才是靠谱预估。

### 7.2 Python 后台任务三大陷阱

**陷阱 1：输出缓冲。** `python script.py > file` 默认全缓冲（8KB），后台任务可能 10 分钟零输出——进程在跑但你看不到。**解决**：`python -u` 或每个 print 加 `flush=True`。

**陷阱 2：f-string 格式符作用域。** `f"{x:.2f if x else 'N/A'}"` 是**错误的**——`:.2f` 会被应用到整个 `x if x else 'N/A'` 表达式，字符串 `'N/A'` 遇到 `.2f` 直接 ValueError。**正确写法**：先算值再格式化：
```python
s = f"{x:.2f}" if x is not None else "N/A"
print(f"结果={s}")
```

**陷阱 3：multiprocessing + Numba = 首代静默漫长。** scipy DE 的 `workers=-1` 启动 16 个子进程，每个子进程独立编译 Numba JIT 函数（~30-60 秒/进程）。首代评估可能 5-10 分钟无输出，看起来像卡死，实际在编译。

### 7.3 降维分组是 DE 实战的关键技巧

原方案 25 环独立参数 = **52 个变量**。scipy DE 的种群规模建议是变量数的 5-15 倍，这意味着需要 260-780 个种群成员——完全不可行。

**分组方案**：25 环 → 5 组（每组 5 环共享 W/h），变量数 52 → **12**。

| 指标 | 52 变量方案 | 12 变量方案 |
|------|:---:|:---:|
| 种群成员 | 10 | 5 |
| Phase 1 评估数 | 520 | 130 |
| 可操作性 | ❌ 卡死 | ✅ 跑通 |

**原则**：变量数 > 20 时，先想清楚分组/降维策略。不要让优化算法裸奔高维空间。

### 7.4 polish=True 在昂贵评估下是定时炸弹

scipy DE 的 `polish=True` 会用 L-BFGS-B 对最终解做局部精修。但 L-BFGS-B 需要梯度，12 个变量 = 有限差分一次梯度 = **24 次额外评估**。如果用 full-60 评估（53 秒/次），单步梯度就要 21 分钟。

实测数据：Phase 2 的 8 代 DE 用了 1800 秒，但 polish 额外吃了 **2600 秒**（比 DE 本身还长）。

**规则**：评估函数 > 10 秒时，关掉 polish，或者只用 noon schedule 做 polish。

### 7.5 约束边界上的优化行为

DE 找到的最优解 P = 60.52 MW——**刚好贴着 60MW 约束线**。这不是巧合。

当目标 = 最大化 P/A 且约束 = P ≥ 60 时，最优解必然在约束边界上（因为 P/A 随 P 增大而递减——更大的功率意味着更多镜子、更大面积、更低单位效率）。DE 天然会"推"到边界。

**启示**：如果最终解功率远高于 60 MW（如 65 MW），说明约束没绑紧或罚系数不够大。

### 7.6 校准系数不是常数

本轮的校准系数 k = 0.923 是 n_rings=23/25/27 三个点的均值。但实际各点差异显著：

| n_rings | k |
|---------|----|
| 23 | 0.935 |
| 25 | 0.929 |
| 27 | 0.905 |

外环越多 → noon 和 full 差距越大 → k 越低。用单一均值做校准会有系统性偏差，但 Phase 2 的 full-60 精修可以兜底。

**更好的做法**：如果计算资源允许，校准时覆盖更广的 n_rings 范围，或直接用 full-60（Phase 2 的作用正是此）。
